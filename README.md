# booth-notify — コワーキングの個室ブース予約を「電話なし・費用0円」で回す GAS

コワーキングスペースの個室（電話ブース）の予約が、**経営者への電話 → ホワイトボードに手書き** でしか受けられず、会議中は取りこぼしていた。
この Google Apps Script は、Googleカレンダーの「予約スケジュール」を予約の入口にして、その周りの3つの困りごとを既にある道具だけで埋める。

| ファイル | 何をするか | 使っている「あるもの」 |
|---|---|---|
| `Code.gs` | 予約の確定／キャンセル通知メールを5分おきに検出し、**Slackへ投稿**（既存Botを流用） | Gmail・Slack・既存Bot |
| `Board.gs` | **館内モニター用のフィード**。予約済みの時間帯をJSONで返すWebアプリ（店内の遊休モニターが60秒おきに取得） | Googleカレンダー・遊休モニター |
| `Holiday.gs` | **休業日の予約枠を自動で塞ぐ**。営業日カレンダーに「営業日」が無い平日にブロック予定を作る。営業日に戻れば自動解除 | 営業日カレンダー（公開ICS） |

- 追加費用 0円（GAS・Googleカレンダー・Slack の無料枠のみ）
- 経営者の操作はゼロ。予約は自動確定し、Slack通知は「事後報告」＝見逃しても事故にならない
- 公開1週間で16枠（8時間分）の予約が入った。導入前は電話受付で記録が残らず計測すら不能だった

## 設計で大事にしたこと

- **誰にも新しい操作を求めない**。外の人はサイトで予約するだけ、店内の人はモニターを見るだけ、経営者は普段のSlackを見るだけ
- **落ちない**。Slack投稿に失敗したらラベルを付けない＝次回5分後に自動リトライ。モニター用フィードは失敗時も `ok:false, busy:[]` を返して枠組みを残す
- **名前は店内にだけ出す**。モニター用フィードは公開URLなので、予約者名はスクリプトプロパティのキーが一致した応答にしか含めない（`?staff=キー` を店内モニターのURLにだけ付ける）
- **失敗から同日修正**。臨時休業日に予約が入る事故が起きた日に `Holiday.gs` を追加した

## スクリプトプロパティ（GASエディタ → プロジェクトの設定）

| キー | 内容 | 必須 |
|---|---|---|
| `SLACK_BOT_TOKEN` | Bot User OAuth Token（`xoxb-…`） | ✅ |
| `SLACK_CHANNEL_ID` | 投稿先チャンネルID（`C…`） | ✅ |
| `SLACK_MENTION_USER_ID` | 通知でメンションする人のメンバーID（`U…`）。未設定ならメンションなし | 任意 |
| `BOOTH_ICS_URL` | 予約カレンダーの公開ICS URL（CalendarApp が失敗したときの予備経路） | ✅ |
| `OPEN_DAYS_ICS_URL` | 営業日カレンダーの公開ICS URL | ✅ |
| `BOARD_STAFF_KEY` | 店内モニターにだけ予約者名を出すためのキー文字列 | 任意 |

## 設置手順

1. 予約用のGoogleアカウントでGASプロジェクトを作り、3つの `.gs` と `appsscript.json` を入れる（`clasp push` でも可）
2. 上のスクリプトプロパティを設定する
3. `setup()` を実行（Gmailラベル作成＋5分トリガー）、`setupHoliday()` を実行（カレンダー権限の承認＋1時間トリガー）
4. `Board.gs` を「ウェブアプリ・アクセスできるユーザー＝全員」でデプロイし、そのURLをモニター側のページに設定する
5. 配線テスト: `test()`（Slackに🧪テスト通知が1件飛ぶ）／`testBoardFeed()`／`testHolidayParse()`

## 運用で踏んだ落とし穴（同じ穴を避けるために残す）

- **`clasp push` だけでは本番の Webアプリに反映されない**。`/exec` はバージョン固定なので `clasp deploy -i <デプロイID>` でバージョンを進める。反映確認は応答の `rev`（`BOARD_CODE_REV`）で
- **`clasp deploy` でバージョンを進めると匿名アクセスが403になる**ことがある。GASエディタの「デプロイを管理」で設定を変えずに「デプロイ」を押し直すと数秒で戻る
- 予約通知メールの送信元は `calendar-notification@google.com` ではなく**カレンダー所有者アカウント自身**。送信元の決め打ちで0件ヒットになった障害があったので、件名で検出している
- スコープを増やした push の後、再承認するまで既存のトリガーも止まる。ラベル方式なので通知は失われず、再承認後に自動で追いつく
- 公開ICSには CORS ヘッダが無く、ブラウザのJSから直接読めない。GASを1枚挟んでJSONにしている

## トラブルシュート

- 通知が来ない → 実行ログを見る。`not_in_channel`（Botを /invite し忘れ）／`channel_not_found`（ID間違い）／`invalid_auth`（トークン間違い）が定番
- 原因が分からない → `diagnose()` を実行。トリガーの有無・検索クエリのヒット数・直近の受信メール（送信元と件名だけ）をSlackと実行ログに出す
